# Подготовка к защите

## Как приложение находит Redis

REDIS_HOST=redis задан в окружении app через Compose. Оба контейнера подключены к пользовательской сети kr2_backend. Встроенный DNS Docker разрешает имя сервиса redis в адрес его контейнера; фиксировать этот IP вручную не нужно.

## Адрес клиента

Строка client в /whoami берётся из X-Real-IP, который Nginx устанавливает равным своему $remote_addr. При обращении с Mac по Host-only ожидается 192.168.56.2. Входящее TCP-соединение приложения устанавливает Nginx через опубликованный Docker-порт, поэтому адрес TCP-пира обозначает прокси или сетевой шлюз, а не первоначального клиента.

## Вопросы к защите

1. **Loopback и публикация.** 127.0.0.1 внутри контейнера — его собственный loopback. Перенаправление Docker приходит на сетевой интерфейс контейнера, поэтому слушать нужно 0.0.0.0:8001. Привязка на Ubuntu 127.0.0.1:8001:8001 по-прежнему не публикует порт во внешней сети.
2. **Пароль в истории.** Удаление .env новым коммитом не делает старый пароль секретным. Его нужно заменить. Историю опубликованного main можно очистить только согласованно, например git-filter-repo с последующим обновлением удалённых ссылок и копий участников; одной очистки без ротации недостаточно. Для КР2 сохранён исходный шаблон в main, а на VM создан независимый случайный пароль.
3. **Слои образа.** RUN rm .env удалит файл только из итогового представления файловой системы. В более раннем слое его содержимое останется, и получатель образа сможет извлечь его. Файл нужно исключать из контекста до сборки, а раскрытый пароль менять.
4. **Exec-форма.** Она запускает Gunicorn напрямую, без /bin/sh -c перед ним; процесс получает сигналы Docker как PID 1. Проверка: docker exec <контейнер> sh -c 'tr "\000" " " < /proc/1/cmdline'. В тесте остановка заняла 0.20 секунды.
5. **Подстановка переменных.** ${REDIS_PASSWORD} раскрывает Compose до создания контейнера, сначала из окружения оболочки, затем из .env. $$ оставляет знак доллара для оболочки внутри контейнера при healthcheck. env_file явно передаёт пароль обоим сервисам. При ${...} в healthcheck пароль будет подставлен заранее и попадёт в сохранённую команду проверки; при расхождении окружения оболочки и env_file проверка может использовать другой пароль.
6. **Пользователь Redis.** Официальная точка входа, получив redis-server от root, подготавливает каталог данных и понижает привилегии до redis. Начальный sh -c обходит эту ветку. Проверяются docker compose top и поле Uid в /proc/1/status; UID должен отличаться от 0.
7. **Зачем пароль без публикации.** К Redis могут обратиться другие контейнеры той же сети и процессы хоста; при компрометации приложения закрытый внешний порт не даёт полной защиты СУБД. Пароль добавляет проверку доступа. Пользователь, управляющий Docker, всё равно имеет доступ к секрету.
8. **Готовность.** depends_on без условия ждёт запуска процесса контейнера, но не готовности Redis. service_healthy ждёт успешного PING. Иначе первые запросы к / могут вернуть 500 из-за отказа подключения или аутентификации, хотя /health отвечает ok.
9. **Данные и тег.** down сохраняет именованный том; down -v удаляет его. latest может переключить основную версию Redis, изменить поведение и формат данных; миграцию проверяют отдельно и делают резервную копию. redis:7-alpine сохраняет основную версию 7, но получает обновления внутри неё.
10. **Сертификат и SNI.** Сертификат devops.local не содержит SAN api.devops.local и не является доверенным корнем нового самоподписанного сертификата. curl с devops.crt для нового домена не пройдёт проверку доверия. Nginx выбирает сертификат по SNI в TLS ClientHello; при отсутствии совпадения используется сервер по умолчанию.
11. **Заголовки клиента.** client отражает X-Real-IP от Nginx. TCP-пир приложения — не исходный Mac. Клиент может сам прислать X-Forwarded-For, поэтому нельзя безусловно доверять его первому адресу; нужно учитывать только доверенные прокси. X-Real-IP здесь перезаписывается Nginx значением $remote_addr.
12. **Перезагрузка.** ssh, ufw, nginx и docker запускаются, если включены в systemd. Политика unless-stopped запускает контейнеры автоматически, кроме остановленных вручную. Зависимость Compose не является отдельным системным менеджером после reboot: сервисы должны также уметь переживать краткую недоступность зависимостей. Именованные тома сохраняют данные.
13. **hosts.** Клиент на Mac должен разрешить домен в адрес Host-only. Nginx на VM использует входящий Host/SNI для выбора server, а proxy_pass направлен на числовой 127.0.0.1; для этого обратному прокси не нужна запись hosts о самом себе.
14. **Ошибочная публикация.** 8001:8001 создаёт внешнюю публикацию Docker; правила DNAT и forwarding не эквивалентны обычному INPUT UFW. Раздел 5 старого аудита проверяет только 5000 и 5432, поэтому пропустит 8001. Раздел 6 сравнивает docker compose port app 8001 со строго ожидаемым 127.0.0.1:8001 и отклоняет публикацию на всех адресах, включая IPv6.

## Диагностика по цепочке

- Нет TCP-соединения: проверить разрешение имени на Mac, маршрут, UFW, сокеты и службу Nginx.
- Ошибка TLS: проверить SAN, срок, выбранный SNI сертификат и файл --cacert. Не заменять это постоянным использованием -k.
- 502 от Nginx: проверить kr2.error.log, состояние app и локальный /health, адрес и порт proxy_pass.
- /health отвечает ok, а / возвращает 500: проверить соединение app с redis, имя REDIS_HOST, готовность Redis, пароль и журналы приложения.
- 403 при статическом ресурсе: проверить права файла и проход по каталогам от www-data, затем журнал Nginx.

На защите не использовать reboot или восстановление снимка: найти отказавшее звено, подтвердить вывод журналом и исправить конкретную причину.
